Un starter ahorra tiempo solo si quieres sus decisiones. Sushi SaaS es una base de código para equipos que conectan identidad, tenancy, cobros, uso y operaciones; no evita comprender esos sistemas.

## Elige Sushi SaaS cuando

- Next.js, TypeScript, PostgreSQL, Drizzle, Better Auth y Stripe coinciden con tu pila.
- Los clientes trabajan solos o en equipo y cobros, créditos, archivos, tareas y límites pertenecen a una organización.
- Dinero y uso requieren idempotencia, libreta inmutable, replay de webhooks y conciliación.
- Vas a operar almacenamiento privado, email transaccional, rate limits, trabajos durables y errores localizados.
- Soporte necesita una consola separada con MFA, roles de lectura/escritura, moderación, inspección de cobros y auditoría.
- El equipo valora y mantendrá fronteras obligatorias y tests de fallos.

El beneficio no es el número de páginas, sino que estos sistemas comparten un modelo de tenant e invariantes.

## Elige algo menor cuando

- Validarás demanda con una landing o prototipo desechable.
- El producto es individual, no cobra, o una plataforma alojada de identidad y datos reduce operaciones.
- Base de datos, framework, identidad o cobros requeridos chocan con la pila incluida.
- Necesitas no-code alojado en vez de código propio.
- Sustituir tenancy o cumplimiento costaría más que empezar desde una base estrecha.

## Estrategias de adopción

### Conservar la base

Cuando encajan casi todas las fronteras. Sustituye marca y dominios de ejemplo, configura proveedores y crea el flujo diferenciador. Es la vía rápida y mantiene comprensibles las actualizaciones.

### Retirar capacidades completas

Cuando encaja la arquitectura pero no un dominio. Retira verticalmente UI, rutas, servicios, modelos, esquema, config, trabajos, tests y docs; no ocultes solo la navegación dejando una ruta de datos sin dueño.

### Copiar un patrón

Para una app existente. Lleva migraciones, restricciones, tests y operación junto con el código. Una función de créditos sin clave idempotente ni regla de base no es el mismo patrón.

### Empezar en otra base

Correcto si cambia la pila o el modelo de propiedad. Un starter debe reducir decisiones futuras, no crear una larga reescritura antes del producto.

## Coste tras clonar

Sigues siendo responsable de proveedores, secretos, precios, impuestos, reembolsos, textos legales, retención, monitorización, accesibilidad, amenazas e incidentes. Al sustituir los mocks de imagen/vídeo, configura admisión explícita en producción y valida los tipos de salida reales. Decide si Content Studio, marketing, reservas y referidos pertenecen al producto y fija objetivos reales de recuperación.

“Orientado a producción” significa que el repositorio expone responsabilidades y controles; no certifica tu despliegue.

## Comprobación de una hora

1. Ejecuta [Inicio rápido](/es/docs/quick-start) y abre Web, Admin y Content Studio opcional.
2. Mapea capacidades obligatorias a páginas y servicios reales.
3. Marca **conservar**, **cambiar** o **retirar** para pila, organizaciones, cobros, créditos, storage, jobs, locales, admin y referidos.
4. Traza un flujo de dinero o autorización y lee sus tests.
5. Estima la columna “cambiar”; si domina, elige una base menor.
