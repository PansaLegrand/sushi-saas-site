> Vérifié avec le commit [`35e64b9`](https://github.com/PansaLegrand/sushi-saas-template/tree/35e64b91f4bb62dffea2ab928316eebc3d346cc9).

Commencez par **Core** : l’app client, le worker durable, PostgreSQL, Redis et le stockage local privé. Le premier objectif est de vous connecter à un espace de démonstration et de consulter son registre de crédits. Aucun compte Stripe, email ou fournisseur d’IA n’est nécessaire pour ce parcours local.

## Choisir votre point de départ

| Profil | Applications lancées | Quand le choisir |
| --- | --- | --- |
| **Core — recommandé pour commencer** | App client + worker durable | Pour évaluer le starter ou construire votre produit. |
| Operations | Core + console admin | Pour gérer facturation, jobs et assistance client. |
| Publishing | Operations + Content Studio | Pour ajouter l’application indépendante de rédaction. |

Vous pourrez ajouter les autres applications plus tard. Les profils sélectionnent des outils et cibles de build, sans changer les forfaits, les permissions ou les routes API disponibles.

## 1. Préparer votre machine

- Git
- Node.js `>=24.22.1 <25` (`.nvmrc` indique la version testée)
- pnpm `10.22.0`
- Docker avec Compose, démarré en local

## 2. Lancer Core

Exécutez ces commandes dans un terminal. La branche part de la révision vérifiée pour garder le code et les instructions alignés.

```bash
git clone https://github.com/PansaLegrand/sushi-saas-template.git
cd sushi-saas-template
git switch -c my-saas 35e64b91f4bb62dffea2ab928316eebc3d346cc9
export SAAS_STARTER_PROFILE=core
pnpm starter core install
pnpm starter core setup
pnpm dev:seed
pnpm starter core doctor
pnpm starter core dev
```

Laissez le terminal ouvert, puis rendez-vous sur [localhost:3000/login](http://localhost:3000/login).

Setup crée les fichiers d’environnement ignorés manquants, démarre PostgreSQL, Redis et Garage, crée les bases locales app/test et de restauration, applique les migrations Drizzle et prépare le bucket privé `sushi-dev`. Core omet l’installation, les fichiers d’environnement, la base et les migrations de Content Studio. Vous pouvez relancer setup : il ne remplace jamais un fichier d’environnement existant.

`doctor` vérifie en lecture seule outils, limites d’environnement, infrastructure, migrations, stockage et ports sans afficher les secrets. Le lanceur vérifie doctor, démarre web et worker, puis arrête les deux avec `Ctrl-C`.

Exportez `SAAS_STARTER_PROFILE=core` dans chaque terminal utilisé pour `pnpm lint` ou les commits après l’installation filtrée. Ces commandes `export` utilisent un shell POSIX ; sous PowerShell, utilisez `$env:SAAS_STARTER_PROFILE="core"`.

## 3. Obtenir votre premier écran fonctionnel

1. Connectez-vous avec `demo@example.test` et `DemoPass123!`, ou le mot de passe défini avec `DEV_SEED_PASSWORD` avant le seed.
2. Ouvrez **Compte → Crédits**. Sur une installation neuve, l’espace démo dispose de **1 000 crédits** et de l’écriture correspondante.
3. Ouvrez **Compte → Profil et sécurité** pour explorer les réglages. Votre espace et votre session utilisent maintenant la véritable application locale.

Ces identifiants sont réservés au développement local. Le seed crée un compte vérifié avec domaine réservé et répare les fixtures sans attribuer deux fois le même crédit. Aucun email n’a besoin d’être envoyé. Une activité démo existante peut modifier le solde affiché.

Dans un autre terminal, vérifiez les services :

```bash
curl http://localhost:3000/api/health
curl http://localhost:3000/api/ready
pnpm test:fast
```

Arrêtez le lanceur avec `Ctrl-C` avant de compiler : les modes développement et production partagent `.next`.

```bash
pnpm starter core build
```

Le build conserve la suite de tests racine et prépare le runtime du worker. Pour les parcours navigateur avec stockage local réel et jobs simulés dans un environnement jetable, consultez [Tests et CI](/fr/docs/testing-and-ci).

## 4. Personnaliser votre produit

Exécutez `pnpm customize` pour définir identité, apparence et langues. Continuez avec [Personnalisation](/fr/docs/customize-your-product) et [Architecture](/fr/docs/architecture-and-errors). Configurez les services externes lorsque la fonctionnalité choisie le nécessite : [Configuration d’environnement](/fr/docs/environment-configuration).

## Ajouter des applications au besoin

Arrêtez le lanceur actuel avant de changer de profil. Pour ajouter l’admin sur `http://localhost:3001` :

```bash
export SAAS_STARTER_PROFILE=operations
pnpm starter operations install
pnpm starter operations setup
pnpm starter operations dev
```

Suivez [Configurer la console admin](/fr/docs/admin-console-setup) pour les accès opérateur et le MFA ; le compte client démo n’est pas automatiquement administrateur.

Pour ajouter également Content Studio sur `http://localhost:3002/admin` :

```bash
export SAAS_STARTER_PROFILE=publishing
pnpm starter publishing install
pnpm starter publishing setup
pnpm starter publishing dev
```

Publishing prépare la base Payload et ses migrations séparées. Conservez une authentification et une base distinctes du SaaS ; voir [Content Studio et marketing](/fr/docs/content-studio-and-marketing).

Tous les profils proposent `doctor`, `lint`, `build` et `--dry-run`. Sans profil sélectionné, `pnpm setup`, `pnpm dev:all` et `pnpm build` gardent la stack complète. Pour le customizer interactif complet, utilisez `./scripts/setup.sh development` sans `SAAS_STARTER_PROFILE` dans le shell.

## Réinitialiser les données locales volontairement

```bash
pnpm dev:reset -- --dry-run
pnpm dev:reset
```

Prévisualisez d’abord les cibles. Reset refuse les services externes, exige une confirmation, ne recrée que les données de ce projet Compose, réapplique les migrations et relance le seed sauf indication contraire. Il conserve les profils d’environnement. Un redémarrage normal ne nécessite pas de reset.
